## Defects Found (structured defect-list)

D1. PIN-DEPTH — plan.md:L98-101 + spec.md:L119-121 — The plan installs the finder "with `add-hook` at the maximum depth (90 or higher) so later `add-hook` calls at default depth or with APPEND still sort before it (AC-PIN-003)". This is false at depth 90. `add-hook … t` means depth 90, and for equal positive depth `add-hook` puts the newer function after the older one (subr.el `add-hook`: `(if (< 0 depth) (append …))` followed by a stable sort). Batch probe: finder at 90, then `fake0` (depth 0), then `fakeA` (APPEND) → `(fake0 finder fakeA)`, so AC-PIN-003 fails. Finder at 100 → `(fake0 fakeA finder)`. REQ-PIN-002's "after any member added later by another module or package" also cannot be met: a later addition at equal or higher positive depth sorts after the finder, and the `add-hook` docstring advises against using 100. — Severity: major — Class: blocking — Required fix: in plan D-2, require a depth strictly greater than 90 (e.g. 95 or 100) and drop "90 or higher". Rewrite REQ-PIN-002 to guarantee "after every member added at default depth or with APPEND (depth ≤ 90)", and say that members added at a higher positive depth are not excluded.

D2. PIN-AC013-CAPTURE — acceptance.md:L155-166 — AC-PIN-013 says to capture "the `f` command's completion candidates" and expand "each … against R". With the preferred D-4 option (i) (`project-find-file-in` with `dirs` = (R, N)), `all-files` is absolute: `project-files-relative-names` only applies to a single dir (project.el L329-334), and only `project-find-file` binds it. The default `project-read-file-name-function` (`project--read-file-cpd-relative`; the repo does not customize it) shows candidates relative to the common parent of all files, which here is the sandbox, not R. Expanding `source/a.txt` against R gives `R/source/a.txt`, so a correct implementation fails the AC as written. — Severity: major — Class: blocking — Required fix: capture at `project-read-file-name-function` (stub it to record its ALL-FILES argument, which is absolute) and compare that set. Alternatively expand candidates against the common parent directory the reader uses, not against R.

D3. PIN-AC011-K — acceptance.md:L134-142 — The `k` clause requires "`k` asks about R's project name", but the Given has no live buffer under R. `project-kill-buffers` (project.el L1726-1740) only calls `yes-or-no-p` when `bufs` is non-empty; otherwise it messages "No buffers to kill". The assertion cannot be observed. (Related test-writing trap: `project-compile` uses `call-interactively #'compile`, so the `compile` stub must be an interactive lambda.) — Severity: major — Class: blocking — Required fix: add a live file buffer visiting a file under R (e.g. AC-PIN-012's P1) to the Given. Assert that the stubbed `yes-or-no-p` was called and that its prompt contains `(project-name …)` of R's project.

D5. PIN-NOTES-SCOPE — spec.md:L77-79, L104-108, L175-182 vs L158-171, L277-283 — The glossary's "Projectless buffer" covers any buffer with no own project. Plan A.1 L32-34 confirms notes buffers are projectless (`~/project-notes` has no `.git`).
