How trust flows (and where it breaks)

Plain words: an air-gap (a machine with no internet) can't download anything, so everything it needs is checked in to git. The question a security review asks is: at each hand-off, what proves the bytes are the ones you meant? The chart below is that chain. The dashed red arrow is the gap behind Finding 1.

F1 — Stale committed CLI binary High · confirmed

Plain words: the air-gapped machine runs a pre-built program (imoogi-toolchain) that's checked into git. That program was built one commit before basedpyright was added, so it doesn't know basedpyright exists and refuses to install anything. It works on your Mac only because your local install was made from a fresh build, not the committed file.

Worked example — how I proved it. A reproducible build means the same source always yields byte-identical output, so hashes can be compared.

$ go build -trimpath -buildvcs=false -ldflags="-buildid= -X main.version=1.0.0" ./cmd/imoogi-toolchain   # at HEAD
491492881ff4…   (fresh build)
a5ea1ffa79f3…   (committed binary)          ← mismatch

$ git archive 5808620 | … go build …        # one commit earlier
a5ea1ffa79f3…                               ← exact match: build IS reproducible, binary is just old

$ strings imoogi-toolchain | grep -c basedpyright
0   (committed)      8   (HEAD build)

$ imoogi-toolchain setup                    # committed binary, in a replica of the air-gap repo
imoogi-toolchain setup: no provider for component "basedpyright" kind "python-language-server"
exit=10

Control gap. buildBootstrap skips the rebuild whenever a binary and its provenance.json already exist, and validateBootstrapProvenance only checks that the two match each other. Nothing ties either to the source commit — so a stale or tampered binary passes fetch's own check.

Fix. Have fetch always rebuild into staging and compare with the committed hash (fail loudly on mismatch); refresh binary + provenance together; record the source commit SHA in provenance. A CI/test gate doing the same go build && shasum catches it too.

F2 — Devcontainer sandbox Medium · local-only

Plain words: the container exists to safely run an AI agent with permission checks off (alias cc="claude --dangerously-skip-permissions"). A firewall limits where it can talk. But the agent is allowed to run the firewall script as root without a password — and that script has an --off switch. The thing being contained can uncontain itself.
  • /etc/sudoers.d/node-firewall: node ALL=(root) NOPASSWD: /usr/local/bin/init-firewall.sh + script accepts --off → sudo init-firewall.sh --off removes all egress rules.
  • Egress: tcp/22 to any host and DNS (53) to any host — both are classic tunnel/exfiltration channels; the domain allowlist is resolved to IPs once at start and rots.
  • Unpinned: lazygit via curl | tar from "latest release" (no checksum), npm install -g …@latest, uv:latest.

Fix. Move --off into a separate root-only script; restrict 22/53 to the hosts you need; pin versions and checksums. Note .devcontainer/ is gitignored, so this affects only this machine.

F3 — Opaque binaries without re-verifiable provenance Medium

Plain words: the design says "git commit = the lock" — fine. But several committed files are compiled binaries (you can't read them), and nothing records exactly what they were built from, so a year from now nobody can re-check them.
  • 12 tree-sitter .dylib built by scripts/build-grammars.sh from git tags (tags can be moved), no commit SHA, no output hashes, compiler warnings hidden (2>/dev/null).
  • vendor/ghostel-module/ghostel-module.dylib (1.2 MB): only a version string 0.34.0; no hash, no release URL.
  • 313 committed .elc (byte-compiled Lisp): no mechanism confirms they match their .el source.
  • packages.lock: names + versions only; archive column is ?; no hashes.

Fix. Record commit SHA + SHA-256 per grammar; hash + upstream URL for the ghostel module; a rebuild-and-compare step on the online machine for grammars and .elc.

F4 — Online fetch hardening Low–Medium

Plain words: the first time something is downloaded, its hash is written into the lock and trusted forever (TOFU — trust on first use). A few extra checks at that moment would make the lock more than "whatever the server sent that day".
  • npm tarballs (typescript, typescript-language-server, basedpyright): no independent hash on first fetch (validate is nil or a file-presence check). Registry dist.integrity is same-channel, so the gain is marginal — but it's free.
  • node: SHASUMS256.txt is fetched from the same origin as the tarball; the GPG-signed SHASUMS256.txt.sig is not verified.
  • buildGopls / buildBootstrap: go inherits os.Environ(), so GOFLAGS, GONOSUMDB, GOINSECURE, GOPROXY from the shell silently bypass the checksum database.
  • http.DefaultClient has no timeout; download has no body-size cap.

F5 — vendor.el TLS posture Low

It runs as emacs --batch -Q, so gnutls-verify-error t from early-init.el is not loaded; package-check-signature stays at its default; MELPA packages carry no signatures at all. What Emacs actually does with a bad certificate in batch mode was not executed — only the configuration was read.

F6 — .local/bin PATH prepend Low

imoogi-lsp-prepend-local-bin puts a git-ignored, user-writable directory first on PATH and exec-path for every subprocess Emacs spawns. It validates the symlink's shape, not the bundle's contents. Anyone who can write there as your user can shadow any binary name — but that attacker already has your account, so: low.

What's done well (keep it)

Plain words: these are the places a reviewer normally finds bugs, and they're clean. Worth saying so, so nobody "simplifies" them away.
  • internal/artifact/artifact.go — extracts into a staging dir then renames atomically; refuses absolute/escaping paths, hardlinks, devices; symlinks only relative, in-archive, non-chained; O_EXCL on every file; entry/size caps.
  • internal/setup/setup.go — flock against concurrent runs; probes execute with PATH=/usr/bin:/bin, HOME=<tmp>, NO_PROXY=*; whole-bundle tree SHA-256 recorded and re-checked; lock artifact paths validated (config.go:325).
  • All 5 toolchains.lock.json artifacts: size + SHA-256 OK against the committed files.
  • Boot path makes no network calls; ffap-machine-p-known 'reject; clojure-ts-ensure-grammars nil; ghostel-module-auto-install nil; gnutls-verify-error t in early-init.el.
  • No secrets found in tracked files (pattern scan).

What I did not verify

  • Not read in full: internal/cli/cli.go, internal/config/config.go, the 87 vendored elpa packages, tests/docker/.
  • Secrets scan covered git ls-files only — untracked .moai/, .claude/, .omc/, .omx/ were not scanned.
  • Batch-mode TLS/NSM behavior of vendor.el not executed.
  • Emacs modules reviewed statically only.

Action items

  • F1 Rebuild + recommit the CLI binary and provenance.json; add a rebuild-and-compare gate to fetch (or CI).
  • F2 Remove --off from the sudo-allowed script; tighten ports 22/53; pin devcontainer installs.
  • F3 Record commit SHA + SHA-256 for each grammar and the ghostel module; add an .elc rebuild check.
  • F4 Scrub Go env in fetch (GOFLAGS=, GONOSUMDB=, GOINSECURE=); add HTTP timeout + size cap; optionally verify node's GPG signature.
  • F5 Set gnutls-verify-error t and network-security-level 'high inside vendor.el.

What to check yourself: on any machine, run go build -trimpath -buildvcs=false -ldflags="-buildid= -X main.version=1.0.0" -o /tmp/t ./cmd/imoogi-toolchain && shasum -a 256 /tmp/t vendor/toolchains/cli/1.0.0/darwin-arm64/imoogi-toolchain — the two hashes should be identical. Today they are not.
