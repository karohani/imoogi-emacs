# lens: codebase-precedent

## codebase-precedent

### findings

- **No model/template/CSS precedent exists anywhere in the repo.** The AnkiConnect client implements exactly 10 actions and none of them touch note types: `Handshake, DeckNames, CreateDeck, ModelFieldNames, AddNote, UpdateNoteFields, UpdateNoteTags, NotesInfo, ChangeDeck, DeleteNotes`. There is no `modelNames`, `createModel`, `updateModelStyling`, `updateModelTemplates`, or `storeMediaFile`. Adding them means extending the `AnkiConnector` interface (`var _ AnkiConnector = (*Client)(nil)`) plus the `fakeClient` test double in one step.
- **No CSS exists in the repo at all** (`find . -name "*.css"` outside vendor → zero hits). The only styling precedent is a ~6-line inline `<style>` block in `const browserShell` in `internal/orgpreview/server.go:754-764` (light-only, hard-coded hex, `system-ui` font). No `night_mode`/`nightMode`/`prefers-color-scheme`/`data-theme` anywhere. No `//go:embed` anywhere in `internal/` or `cmd/` — a template/CSS asset would be the first embedded asset in the Go tree (existing precedent is Go string constants, not embed).
- **No LaTeX/MathJax handling anywhere.** `internal/anki/orgdoc/orgdoc.go` `renderFragment` is a bare `org.New().Parse(...).Write(org.NewHTMLWriter())` with no pre- or post-processing. `internal/orgpreview/parser.go` has a hand-rolled inline-markup pass (`splitDelimited` for `*`, `linkRE`) but no math rule. So there is zero in-repo regex precedent for `$`/`\(` handling.
- **A close precedent for the "post-process go-org output" hook does exist**, in the same file: `clozeMarkerPattern = regexp.MustCompile(\`\{\{c\d+::\`)` plus a documented "go-org passes X through verbatim (research.md §2)" argument. The math/image transform is the same shape of change and belongs in the same function.
- **Image/relative-path resolution has a strong in-repo precedent**: `internal/orgpreview/assets.go` `AssetResolver.Resolve(baseFile, target)` — URL-unescapes, rejects non-empty and `file:` schemes, joins relative targets against `filepath.Dir(baseFile)`, canonicalizes via `filepath.Abs` + `EvalSymlinks` (tolerating `os.IsNotExist`), and confines the result to allowed roots via `within()`. `internal/orgpreview/parser.go:33` gives the org link regex actually used in this repo: `` `\[\[file:([^\]\n]+)\](?:\[([^\]\n]*)\])?\]` `` — note it matches only `file:`-prefixed links, so bare-relative `[[x.png]]` and `https:` targets are NOT matched by the existing pattern and would need widening. `isImageTarget(target)` (parser.go:275) is the existing image-vs-link discriminator.
- **The org file's directory is reconstructible in the Go backend today, but only indirectly**: `protocol.Entry.SourcePath` is written by Elisp as `(file-relative-name file root)` (`modules/anki/imoogi-scan.el:117`, serialized at `modules/anki/imoogi-process.el:45,52`), and `protocol.Config.SyncRoot` carries the root. So base dir = `filepath.Join(req.Config.SyncRoot, entry.SourcePath)` → `filepath.Dir`. **`orgdoc.Render(noteType, title, body)` currently receives neither** — its signature must grow a base-path parameter, and it is documented as "a pure function of its inputs: no registry, no AnkiConnect client, no side effects", so media upload cannot live inside it without breaking that stated contract.
- **Hashing precedent is explicit and restrictive.** `hashing.Hash(noteType, fields, deck, tags)` documents a canonicalization contract that is load-bearing for orphan confirmation: it is called a *second* time with values recovered from a `notesInfo` response (modelName / fields map / tags / registry-recorded deck). Any hash input that cannot be recovered from `notesInfo` (e.g. image file content bytes) would break that round-trip equality. However, the *rendered field values* are a hash input — so once `<img src>` is rewritten to a content-hash-suffixed filename, an image content change changes the field HTML and therefore changes the hash for free, with no new hash input needed.
- **Content-hash-suffix helper precedent exists** but in the non-Anki tree: `internal/setup/setup.go:611 fileSHA256` (`sha256.Sum256(data)` + `hex.EncodeToString`), `internal/artifact/artifact.go:45 VerifyFile` (streaming `sha256.New()` + `io.Copy`), `internal/setup/setup.go:532 bundleTreeSHA256`. `internal/anki/hashing` already imports `crypto/sha256`+`encoding/hex`, so a media-name hash fits there or beside it.
- **Registry has no media concept and no schema-version field.** `registry.Entry` is exactly `{note_id, source_path, note_type, resolved_deck, content_hash}`. Adding media tracking means widening this struct; `Load` treats *any* unmarshal failure as `*CorruptError` → `state_unreadable` → run aborts, but adding a new field to a JSON array of objects is backward-compatible on read (old files decode with the zero value). There is a deliberate design statement that the registry holds only "everything recomputable"; orphan handling in this codebase is note-scoped and identifier-based only (`confirmAndDelete`, `computeCandidates`), with no delete path that isn't ID-driven.
- **REQ-021 enforcement is already implemented and is a hard blocker for migrating the 5 test notes**: `planner.go:266-275` — if `regEntry.NoteType != entry.NoteType` the entry is *skipped* with `CodeNoteTypeChangeUnsupported`, no field written, no card moved, registry untouched. There is no in-repo escape hatch. The only existing path that discards a stale identifier and creates a fresh note is `addNewNote`'s reconcile fallback (`planner.go` doc: "the STALE identifier is simply discarded; a fresh one is assigned"), reached only when the registry has no record of the ID.
- **Field-name resolution precedent is exactly the mechanism that makes imoogi-owned models attractive**: `runner.resolveFields` (`planner.go:130-183`) lowercases both sides to map `Front`/`Back`/`Text` onto the user's real field names, caching `ModelFieldNames` per run in `runner.modelFields`. Its doc comment documents the measured hazard ("`updateNoteFields` accepts an unknown field name, answers error:null, and changes nothing") and the `fakeClient.modelFields` comment names the user's actual situation: "a customized 'Basic' carrying lowercase front/back is the observed case this exists to reproduce."
- **Deck names with `::` are confirmed real in this user's collection, with parentheses**: `modules/24-anki.el:53` records the measured value `"(PROGRAMMER)::(GO)"` and the measured failure that `org-global-properties`' `_ALL` mechanism breaks it into `("???" "::" "???")`. This is direct in-repo evidence that a CSS-class normalization rule must handle `::`, spaces, and parentheses. `imoogi-anki-set-deck`'s docstring states the `::` nesting convention ("예: \"Geography::Europe\"").
- **Naming precedent for imoogi-owned artifacts**: `.imoogi-registry.json` (`modules/anki/imoogi.el:93`), `imoogi.json` config (`imoogi.el:64`), `imoogi-` prefix throughout Elisp, `imoogi-anki` binary. `imoogi-Basic`/`imoogi-Cloze` is consistent; note the existing Go constants are bare `NoteTypeBasic = "Basic"` / `NoteTypeCloze = "Cloze"` and the Elisp property completion is hard-coded `"Basic Cloze"` (`24-anki.el:55`), plus `imoogi-anki-mark-basic`/`-cloze` write those literal strings — three places that carry the note-type name.

# lens: external-docs

## external-docs
### findings

**AnkiConnect API (official add-on README, v6 API)**
- `createModel` takes `modelName`, `inOrderFields`, optional `css`, optional `isCloze` (default false), and `cardTemplates[]` with optional `Name`, plus `Front`/`Back` HTML. Cloze note types are created by `isCloze: true` — same action, no separate endpoint. So `imoogi-Basic` and `imoogi-Cloze` are both createModel calls.
- Idempotent model create/update is expressible with exactly the actions named in the topic: `modelNames` (list all model names) → if absent `createModel`; if present `updateModelStyling` (`params.model = {name, css}`) and `updateModelTemplates` (`params.model = {name, templates: {"<card name>": {Front, Back}}}` — "Only specified cards and sides will be modified"). `modelStyling` / `modelTemplates` read the current values back, so a no-op check before writing is possible. `modelFieldNames` returns the field list (the planner's existing field-resolution input).
- `storeMediaFile` accepts `filename` plus exactly one of `data` (base64), `path` (local absolute path), or `url`. `path` means imoogi can upload a local org-relative image without base64-encoding it itself. Companion actions exist for the orphan question: `getMediaFilesNames` (glob `pattern`), `retrieveMediaFile` (returns base64, or `false` if nonexistent — usable as an "already uploaded?" probe), `deleteMediaFile`.
- `addNote` normally rejects duplicates (first-field match on the same note type) unless `options.allowDuplicate` is set — relevant because the imoogi-owned note types are new, so the 5 existing test notes on stock `Basic`/`Cloze` will NOT dedupe against re-adds under the new types.

**Anki special field `{{Deck}}` — exact value format (answers the open question)**
- Official manual lists the special fields: `{{Tags}}`, `{{Type}}`, `{{Deck}}`, `{{Subdeck}}`, `{{CardFlag}}`, `{{Card}}`, `{{FrontSide}}`; names are case sensitive. The manual does NOT state the nested-deck format.
- Anki source settles it: `fields["Deck"] = self._col.decks.name(self._card.current_deck_id())` and `fields["Subdeck"] = DeckManager.basename(fields["Deck"])`. So `{{Deck}}` is the **full deck path including `::` separators** (e.g. `Geography::Europe`) and `{{Subdeck}}` is only the last component. A `class="deck-{{Deck}}"` wrapper therefore emits literal `::` and spaces into the class attribute.
- CSS ident rules (MDN): a class name may contain `A-Z a-z 0-9 - _` and any non-ASCII ≥ U+00A0, or escaped chars; it must not start with an unescaped digit or `-`+digit; identifiers are case-sensitive. `:` and space are not valid unescaped — so a normalization rule is mandatory (e.g. `::`→`-`, whitespace→`-`, lowercase, prefix-guard against a leading digit), and it cannot be skipped by relying on Anki.

**MathJax (answers the AnkiDroid/iOS availability question)**
- Anki manual: "MathJax is supported out of the box on Anki 2.1+, AnkiMobile, and AnkiDroid 2.9+." Delimiters are `\(`…`\)` inline and `\[`…`\]` display; `$...$` / `$$...$$` do **not** apply in Anki. Content must be TeX. Newlines inside must be `<br>`-style (Shift+Enter), a plain newline breaks rendering. Anki has special cloze logic that "might not work if you change the standard delimiters for MathJax equations" — i.e. do not invent custom delimiters, emit exactly `\(`/`\[`.
- AnkiDroid 2.15+ additionally hides card content during MathJax rendering and supports `onUpdateHook`.

**org-mode's own inline-math heuristic (grounds the `$5` requirement)**
- Org manual, LaTeX fragments: "single '$' characters are only recognized as math delimiters if the enclosed text contains at most two line breaks, is directly attached to the '$' characters with no whitespace in between, and if the closing '$' is followed by whitespace or punctuation (but not a dash)." `$$…$$`, `\(…\)`, `\[…\]` and `\begin{...}` environments (begin on its own line, preceded only by whitespace) are also recognized. The manual itself recommends `\(...\)` over `$...$`.

**go-org caveat for the LaTeX transform**
- go-org issue #12 ("Subscript and superscript in LaTeX fragments", closed) reports that `\(\sum_{i=1}^n a_n\)` had its `_`/`^` rendered as `<sub>`/`<sup>`, breaking MathJax. This is a documented hazard for the imoogi transform: whatever go-org version is vendored must be checked, because inline sub/superscript mangling inside math is a known go-org behavior, independent of the delimiter passthrough already measured.

**Anki media conventions (bear on hashing/orphan questions)**
- Media lives in `collection.media`; fields reference it as plain `<img src="filename.jpg">`. Filenames with spaces/`%` display percent-encoded in the editor; the manual advises avoiding spaces and special characters — supports a sanitized `basename + content-hash` naming scheme.
- **A leading underscore makes Anki's Check Media ignore the file** ("Files beginning with an underscore … signal Anki to ignore them during media checks"). Check Media is the user-facing tool that finds and trashes unused media. This is the documented, in-Anki answer to the orphan-media question: Anki already owns unused-media cleanup, so a registry-side media inventory is not required for correctness (note the tradeoff — `_`-prefixed names would be *exempted* from that cleanup, so imoogi should NOT prefix uploaded card images with `_`).

**Night mode CSS class names (they differ per client — a light+dark theme must carry both)**
- Anki desktop manual + AnkiMobile manual: `.card.nightMode { background-color: #555; }`, and `.nightMode .myclass` for descendants.
- AnkiDroid wiki: uses `.night_mode`, explicitly `.card.night_mode` with **no space** between the classes ("contrary to the other examples on this page there should *not* be a space between the `.card` and `.night_mode` classes").
- AnkiDroid wiki also recommends `.card img {max-width: 100%; max-height: none;}` for images and `word-wrap: break-word;` (Android stopped auto-breaking long words since 4.4).

**Out-of-repo SPEC-ANKI-001 lineage — a hard blocker for this new SPEC**
- `spec.md` REQ-016 forbids exactly what this SPEC proposes: "The imoogi system shall not modify Anki review history, card scheduling state, note-type templates, or collection styling, on any code path". `spec.md §1.2`-adjacent scope text repeats it ("note-type templates and collection styling are the user's and Anki's property, never imoogi's"), and `acceptance.md` AC (line 102) asserts "no request in the run addresses any scheduling, review-history, **note-type-template, or collection-styling** endpoint." SPEC-ANKICARD-001 must explicitly amend/narrow REQ-016 (e.g. scope it to *user-owned* note types, permitting create/update of imoogi-owned models only) and update that AC, or it is in direct contradiction with the shipped spec.
- `spec.md §4` + `plan.md D-12` already state the REQ-021 posture for migration: "Converting a note's underlying type requires deleting and re-adding the note under the new type — a manual step for this MVP … and a candidate for a later SPEC." That is the documented precedent for how the 5 existing test notes must be migrated (delete + re-add, not in-place type change).
- `research.md §3.2` records that `notesInfo` returns `modelName`, `fields`, `tags`, `mod`, `cards` and **no deck**, and that hashing (D-6) uses note type + rendered fields + tags + registry-recorded deck — i.e. media bytes are not currently a hash input, and there is no documented AnkiConnect response field that would surface an image's stored content either.
- `research.md §2` records go-org's own stated goal ("support a reasonable subset of Org mode … 80/20") as the accepted-limitation grounding for rendering fidelity.

**C. Hashing / media ordering — a correctness trap, not a preference**
- `confirmAndDelete` recomputes `hashing.Hash(info.ModelName, fieldValuesToStrings(info.Fields), e.ResolvedDeck, info.Tags)` from the `notesInfo` response and treats any mismatch as `delete_candidate_unowned`. Therefore the media upload + `<img src>` rewrite and the LaTeX delimiter transform **must** happen before `hashing.Hash` at `planner.go:243`, and the field text imoogi stores must be byte-identical to what it hashed. If the transform runs after hashing (or only on the outbound request), every imoogi note fails the ownership predicate permanently and orphan deletion silently stops working.
- Consequence for the open question: with a content-hash suffix in the stored media filename, an image content change changes the field HTML → changes the hash → REQ-010 update fires. Without the suffix, image edits are invisible to REQ-010/REQ-011 (steady-state no-op). So the collision-avoidance mechanism and the "does image content trigger update" answer are the same decision.
- `hashing.Hash`'s doc comment warns callers must not depend on hash *format* stability, but the registry stores hashes across runs — any change to rendering (LaTeX delimiters, img rewriting) invalidates every stored hash and produces a one-time mass update of all existing notes.
- Orphan media: no `storeMediaFile`/`deleteMediaFile`/`retrieveMediaFile` reference exists anywhere in `internal/` or `modules/`; `registry.Entry` has no media field. Adding one is forward-compatible (registry is `json.Unmarshal` into `[]Entry`, unknown/missing fields tolerated, whole-file atomic rewrite), but nothing today tracks media.

**D. Migration of the 5 existing notes is blocked by REQ-021 by construction**

**E. go-org rendering constraints (measured from the pinned v1.9.1 source)**
- **Relative image resolution is not currently possible in `orgdoc`.** `Render(noteType, title, body string)` takes no path, and `renderFragment` calls `org.New().Parse(strings.NewReader(s), "./")` — a hardcoded `"./"` base. `protocol.Entry.SourcePath` exists on the wire but is never passed to `orgdoc`. Fixing this changes `Render`'s signature and breaks plan.md D-1's stated contract ("pure function of its inputs: no registry, no AnkiConnect client, no side effects") once upload is involved — needs a two-phase render → collect → upload → rewrite, not an in-render upload.
- **Captioned image links do not become `<img>`.** `RegularLink.Kind()` returns `"image"` only when the link has no description, or when the *description itself* is a `file:`/`http(s):` URL with an image extension; otherwise `l.Description != nil` → `"regular"` → `<a href="a.png">caption</a>`. And in the two-part image case the `src` is taken from the *description*, not the URL. `[[file:diagram.png][My diagram]]` therefore yields a link, not an image.
- **Image extension set is fixed** by `inline.go:68`: `(?i)^[.](png|gif|jpe?g|svg|tiff?|webp|x[bp]m|p[bgpn]m)$` — no `.avif`, `.bmp`, `.ico`. `.webm`/`.mp4` render as `<video>`, which Anki media handling would need a separate decision for.
- `src` is `html.EscapeString`'d before emission, so post-render regex rewriting of `<img src>` must match escaped URLs (e.g. `&amp;` in a filename).
- **LaTeX: go-org *does* parse math into a protected node** — `LatexFragment` with `latexFragmentPairs` covering `\(`/`\[`/`$$`/`$`; `WriteLatexFragment` re-emits `OpeningPair + content + ClosingPair`, and the interior is parsed with `parseRawInline` (raw `Text`, no emphasis/sub/superscript). So the four syntaxes do pass through verbatim, and `_`/`^`/`*` inside math are protected. But `WriteText` still HTML-escapes raw text (`html.EscapeString(t.Content)` when `t.IsRaw`), so `a < b` inside math arrives at Anki as `a &lt; b` — a MathJax-visible transform imoogi does not control.
- **go-org's `$` heuristic is not org-mode's.** `parseLatexFragment` on `$` requires only `start+2 < len(input)` and then `strings.Index` for the next `$` anywhere in the remaining input — no word-boundary/whitespace/digit checks. So `costs $5 and $7` is parsed as a `LatexFragment` `$5 and $7$`… (delimiters preserved, so output looks unchanged, but the interior is silently switched to raw parsing). Any imoogi-side transform that rewrites `$..$` → `\(..\)` will convert this to real MathJax. The org-heuristic requirement is therefore a genuine behavioral divergence from the parser imoogi already uses, not just a formatting nicety.

Since the image transform rewrites `<img src>` to a content-hash-suffixed stored name, a changed image *already* changes the rendered field value and therefore the hash — no separate hash input is needed. `design.md §2.4`'s inputs table is the exact place a new row would go: note type / rendered field values (post-`go-org`) / effective deck / sorted tag set; excluded: source path, heading position, `ANKI_NOTE_ID`.

- **A second-order hazard the prior SPEC's D-9 imposes on any rendering change**: the same D-6 hash is reused as the *ownership predicate* for deletion (`design.md §3` step 11, `plan.md D-9`) — recomputed from `notesInfo`'s returned `modelName`/`fields`/`tags` with deck taken from the registry. Therefore **any change to rendering (MathJax delimiters, `<div class="deck-…">` wrapper, rewritten `<img src>`) invalidates every stored hash at once**, and the run-phase report's residual risk applies: "a real Anki may normalize stored field content (HTML rewriting, entity or whitespace canonicalization) in ways no stub reproduces, and the failure mode remains fail-safe-but-silent — deletion simply stops happening, reported only as `delete_candidate_unowned`" (`progress.md` §residual risk). A `<div>` wrapper in the field content is precisely the kind of markup Anki may canonicalize.

- **The deck-class wrapper interacts with a prior decision, favorably**: interview.md's rationale ("카드 덱 이동 시 타입 변경 불필요(REQ-021 회피)") is consistent with `spec.md` C-8 / REQ-010 / D-10 — deck is a *card* property, moved via `changeDeck`, and the resolved deck is **both hashed and recorded verbatim** in the registry (`design.md:110`, D-6 "Relationship to the registry's resolved deck"). A `deck-{{Deck}}` CSS class introduces no new state: the deck already invalidates the hash on change. But note `{{Deck}}` is rendered by *Anki at review time*, not by imoogi, so it is invisible to `hashing.Hash` — a deck rename changes the rendered class in Anki without imoogi's field content changing (the deck is a separate hash input, so the hash still moves).

- **go-org's rendering limits are already an accepted, documented consequence, not a defect** — `plan.md D-1` consequence: "`go-org` coverage of Org constructs is narrower than `ox-html`. Constructs that render poorly are a documented limitation for this SPEC, not a defect." `research.md §2` grounds this in go-org's own README ("the goal for the html export is to produce sensible html output, not to exactly reproduce the output of `org-html-export`") and enumerates the covered constructs from the `org/` package layout — **math/LaTeX is not in that enumeration**, and neither `research.md` nor `design.md` mentions LaTeX, MathJax, images, media, `storeMediaFile`, CSS, or styling **anywhere**. So the CARD SPEC's measured facts (all four math syntaxes pass through verbatim; `<img src="path as-is">`) are new evidence, not a contradiction of prior findings.

- **Rejected alternative worth not re-litigating**: `plan.md D-1` rejected rendering via Emacs' `ox-html` (which would have given native LaTeX/`org-html` math handling) because "it splits rendering across two languages, requires an Emacs process in the test loop, and makes the back end untestable in isolation".
